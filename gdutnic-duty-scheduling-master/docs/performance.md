# 内存与运行速度优化

2026-11-08，相对于提交 `a36ffa3` 的优化：

- 单个聊天详情通过 `(visitor_id, id)` 主键查询，只读取该会话的消息，避免加载同一访客的其他会话和图片。
- 聊天消息使用 `executemany` 和生成器批量写入，减少 MySQL 往返，不额外构建完整参数列表。
- 超额清理聊天时只统计一次全局用量，此后按被删除会话的大小递减，避免每删除一个会话就重新扫描全部消息。统计口径沿用原有数据库 `LENGTH` 行为。
- 总览只查询所选月份与周的并集，跳过两个区间之间的无关排班，避免日期跨度增加时无效加载和状态计算。

## 本地对比

使用临时 SQLite 数据库，对相同数据分别调用修改前后的函数，并断言返回值完全一致。每项执行三次，耗时取中位数，内存取 `tracemalloc` 测得的最大 Python 分配峰值；不代表进程总内存或线上 MySQL 表现。

| 场景 | 原耗时 | 优化后耗时 | 原峰值 | 优化后峰值 |
| --- | ---: | ---: | ---: | ---: |
| 80 个会话，每个包含一条 200,000 字符消息，读取一个会话 | 17.95ms | 0.34ms | 15.536MiB | 0.386MiB |
| 2024-01-01 起连续 1096 天，每天 4 班、每班 8 人；查看 2024-01 月统计及 2026-11-02 所在周 | 676.16ms | 27.00ms | 19.163MiB | 0.721MiB |

总览的测试时间固定为北京时间 2026-11-02 10:30。上述收益针对数据量和日期跨度较大的场景，实际收益取决于数据分布。
