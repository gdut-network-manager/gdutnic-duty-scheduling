# GDUTNIC 排班签到

网络服务协会的值班排班与签到系统。普通成员用姓名和密码（或 GDUTNIC 单点登录）登录，在概览里查看自己的排班、签到并登记外勤；管理员在管理端维护每日/每周/特殊排班、账号权限、外勤登记与考勤统计，并可限制打卡只能在校内网络完成。界面保留 Material You 风格。


## 一行部署

前提：已下载本项目，安装 Python 3.10+（含 `venv`）和带 Compose 插件的 Docker，并启动 Docker 服务。下面命令均在项目根目录执行。

**Linux / macOS：**

```bash
python3 -m server.init_data && docker compose --env-file data/.env up -d --wait mysql && bash start.sh
```

**Windows（CMD）：**

```bat
python -m server.init_data && docker compose --env-file data/.env up -d --wait mysql && start.bat
```

命令会初始化 `data/`、生成随机数据库密码、启动并等待 MySQL 就绪，再创建 `.venv`、安装依赖并启动应用。任一步骤失败都会停止后续步骤。重复执行保留现有数据库、配置和已修改的用户密码；更新代码前先停止正在运行的应用。

- 成员入口：`http://127.0.0.1:50025/`；其他设备使用服务器 IP 和端口 `50025`。
- 原始管理员入口：复制启动日志打印的随机路径，首次进入可自定义**原始管理员**名称并设置密码（名称留空则使用「原始管理员」）。
- 用户端和管理员登录框均可点击眼睛图标显示 / 隐藏密码；图标随 `icon/` 一起部署，不依赖 `parment/`。
- MySQL 在后台运行并配置为自动重启；应用在当前终端前台运行，按 `Ctrl+C` 停止。需要长期运行时，将应用交给系统服务或进程管理器托管。
- 使用已有或远程 MySQL 时，先配置 `data/.env`，然后执行 `bash start.sh`（Windows 用 `start.bat`），无需启动本地 MySQL 容器。

## 项目各部分使用方法

### 启动与首次配置

```bash
python3 -m server.init_data   # Windows 可用 python；无需先安装依赖
# 自动生成 data/.env 和随机数据库密码；远程数据库请编辑 data/.env
docker compose --env-file data/.env up -d --wait mysql
./start.sh                    # Windows 用 start.bat
```

启动日志会打印管理员地址（形如 `http://127.0.0.1:50025/a8clrf3j`）。首次打开该地址会创建管理员，首个管理员自动获得全部权限。

### 成员端（`/`）

1. 用姓名和密码登录，默认初始密码 `gg2017`；管理员在「其他设置 → SSO 设置」启用并保存后，登录框还会出现「通过GDUTNIC」入口。
2. 「概览」只显示本人在当天的班次，卡片和时间轴展示同班所有伙伴的名称与考勤状态；在班次开始前「提前打卡」分钟内，“确认签到”按钮变为可点，悬停背景为浅绿色。
3. 点击签到后记录到岗时间；若下一班与本班首尾相接（1→2、3→4），会自动一并签到。
4. 概览时间轴下方的「外勤登记」卡片点击按钮登记本月外勤，成功后按钮固定为「登记完成」。
5. 「排班列表」可按周浏览所有已生成排班，完整显示值班人员姓名；不显示考勤状态，卡片保持统一颜色。此入口需要单独授予「排班列表」权限，不随「概览」权限自动开放。
6. 左侧底部可修改密码；修改后持久保存，重启不会恢复为初始密码。
7. 登录后超过「无操作自动退出」设定的时间没有任何操作会自动退出；同一浏览器同一端的多个标签页共享这一计时。

### 管理端概览

- 固定显示本月出勤率、迟到数、旷班数。三个统计药丸保持单行，内容过长自动撑宽，空间不足时整组隐藏。
- 时间轴显示当前值班与人员姓名；下方周历按真实班次显示第一至第四班，缺班留空。只有从「特殊排班」新增的班次才进入特殊排班行；该周有特殊排班时才显示，与第四班间隔一个普通班次行高度，每天按开始时间纵向排列。
- **周排班翻页与整周删除**：周历两侧的箭头查看上一周 / 下一周，范围覆盖有排班的最早到最晚一周；到边界时对应箭头变灰禁用，中间没有排班的周仍可翻到。翻到其他周时标题变为「周排班」，并出现「回到本周」。
- **删除整周排班**：按钮删除当前显示这一周（周一至周日）的全部班次。需在确认卡片输入「删除本周排班」；该周已签到的记录会先归档到出勤历史，仍可在统计中查到，每周模板与账号不受影响。这一周没有排班时按钮自动禁用。
- 点击本周卡片打开详情，再点击某个人名可改判考勤状态。
- **查看日志**：记录管理员与值班账号的操作，按时间倒序显示时间、操作账号、操作内容，可按账号筛选或搜索关键字。覆盖登录、账号增删改、权限与密码变更、排班/特殊排班/每周模板/生成排班/清除排班、调班、考勤与外勤改判、值班签到、外勤登记与确认、系统时间与值班时间设置。页面顶部显示日志表当前占用的存储空间。
  - **容量上限**：操作日志总量超过 10 MB 时自动删除最旧的记录，直到降到 5 MB 以下；因此长期运行时只会保留最近一段时间的记录，更早的审计信息会被清理。检查在每次写入后按固定间隔进行，并在后台每 5 分钟复查一次，无需手动清理。
- **数据管理**：左侧列出可访问的数据表与行数，右侧分页预览记录（每页 50 行，支持表内搜索）。可直接编辑或删除单行；只有白名单中的列可写，主键只读。密码、密钥类字段显示为 `••••••`，也无法通过此页修改——改密码请走用户管理。操作日志不可改写也不可删除；出勤归档只允许删除；**站点设置**只能查看，只能修改允许的数据项，且不能删除整行；**原始管理员（旧版记录）**是只读的历史记录。**管理员账号**的记录同样受保护：没有「用户管理」权限时，数据管理不能停用或删除管理员账号。表名和列名全部来自服务端白名单，请求不会拼进 SQL 标识符。
  - **考勤人员**额外显示所属班次的日期与起止时间（`班次.day` / `班次.start` / `班次.end`），未签到时也能看出这条记录属于哪一班。
  - **多选与批量删除**：点击行内按钮以外的区域即可选中该行（变蓝），按住 Shift 点击可批量选中连续区间；再次点击已选行会取消。底部「清除该页」删除当前页面（含当前搜索条件）的所有行；选中后其左侧出现「清除选中（n）」，取消全部选中后自动消失。两者都需输入确认语，且都会跳过原始管理员。
- **异常统计**（在本周排班下方）：可切换「近 2 周 / 近 4 周」，左右两栏用横向柱状图列出迟到与旷班次数排行，柱右侧标注次数；次数相同按姓名拼音排序。历史不足所选周数时，统计窗口内已有的全部记录。

### 每日 / 每周 / 特殊排班 / 调换值班

- **每日排班**：按日期查看，点击卡片编辑或删除；删除会连同签到记录一起删除。
- **每周排班**：填写四个班次的时间与周一至周日人员，保存后核对勾选；用「下载 CSV 模板」与「一键导入」批量填人。
- **生成排班**：选择开始及截止日期（开始不能早于今天），按星期生成整个区间。已有或冲突班次在无人签到时覆盖，有签到记录时跳过。
- **特殊排班**：新增一次性班次，可在未来特殊排班列表中编辑或删除。
- **调换值班**：选择两位人员和各自的一个未来班次互换，需勾选「双方已协商完成并同意调班」。任一班次开始后不能删除；双方都签到且两个班次结束后，记录自动消失。
- **清除所有排班**：需输入确认语，删除全部班次与签到，保留模板和账号。

### 成员端外勤：登记与确认

- 「概览 → 外勤登记」：按钮分三档 —— `点击登记`（状态 0）→ `等待确认`（状态 1，黄色）→ `登记完成`（状态 2，浅绿色且锁定）。点击只会从 0 变为 1，不会自动确认。
- 「外勤确认」：列出本月所有状态 1 的登记及登记时间。点「点击确认」变绿后卡片稍后消失、状态变为 2；点「删除」卡片立即消失、状态回到 0，可重新登记。
- 数据库 `field_duty.status` 取值 0/1/2；升级前已有的记录按 2（已确认）处理。

### 用户管理

- 顶部搜索框按姓名即时筛选。
- **补全用户**：在「每周排班」的「保存每周排班」左侧，扫描已保存的每周表及已生成排班（含特殊排班），补建缺失账号。新账号默认加入会员组，初始密码 `gg2017`，已有账号密码保持不变。
- **清理多余用户**：在「添加账号」右侧，确认后删除默认会员组中不在上述排班范围内的账号；其他权限组账号不受影响，排班与签到记录保留。
- 卡片右侧可更改权限、更改密码、重置密码、停用/启用、删除账号；SSO 已绑定的账号还会显示「解绑SSO」，解除后该账号需要重新用本地密码验证才能再次绑定。
- 「原始管理员密码」卡片只在原始管理员登录时出现，其他账号即使拥有「其他设置」的全部子项也看不到。
- 「更改权限」弹窗只选择所属权限组；组内访问范围在「权限组管理」中通过折叠树维护。

### 外勤管理（管理员）

- 翻页查看各月参与情况，点击人员卡片切换已参加/未参加。只显示已启用且拥有**成员端「外勤」**权限的账号，列表人数与已参加人数按该范围统计；撤销权限后隐藏，历史记录保留。
- **月份翻页**：与概览的周排班一致，标题行右侧用箭头查看上个月 / 下个月，范围覆盖有外勤记录的最早到最晚月份（本月始终在范围内）；到边界时对应箭头变灰禁用。离开本月后出现「回到本月」。
- **删除整月外勤**：按钮清空当前显示月份的全部外勤记录（含处于「等待确认」的记录），需输入「删除本月外勤」确认。外勤是每月状态而非归档数据，删除后相关人员回到「未登记」，需重新登记并由他人确认；该月没有记录时按钮自动禁用。
- **只统计已确认（状态 2）的外勤**；自己登记但未确认的记录不计入。
- 管理员修改的条目会显示「管理员修改」。

### 其他设置

「其他设置」没有独立入口，只要拥有下面任意一项权限，侧栏就会出现该页面，进入后只显示已授权的卡片；每张卡片对应的接口各自校验权限。

- **打卡设置**：配置打卡与外勤登记可用的来源网络，详见「打卡设置：来源 IP 限制」。
- **SSO 设置**：配置 GDUTNIC 单点登录与账号绑定，详见「GDUTNIC 单点登录」。
- **值班时间**：签到窗口与迟到/旷班阈值。三个时间都从班次开始时间起算：提前打卡为开始前多少分钟起可签到，迟到为开始后多少分钟内签到记为迟到，旷班为超过该时间才签到或不签到。旷班时间必须大于迟到时间。保存后成员端按钮与判定即时跟着更新。
- **无操作自动退出**：见下文「无操作自动退出」；使用「值班时间」权限。
- **系统时间**：默认「自动设置」使用真实时间；取消后可指定日期与小时、分钟，并按该时刻开始计时。签到窗口、迟到/旷班判定、概览统计、外勤月份、调班与生成排班全部使用这个时钟，前端时间轴与按钮也会同步。下方始终显示当前系统时间。
- **SMTP 发件邮箱**：填写服务器、端口、加密方式（SSL / STARTTLS / None）、登录账号与密码、发件邮箱与发件人名称。端口留空时按加密方式取默认值（465 / 587 / 25）。密码只保存在服务器配置中，页面不会回显；
  - 密码框留空表示保留原密码，清空存储需要显式提交空值。
  - 启用前必须填好服务器地址与合法的发件邮箱，否则拒绝启用。
  - 「发送测试邮件」会弹窗索取收件地址，用当前配置实际发一封测试信并把成功或失败原因写在卡片内。
  - 实现位于 `server/mailer.py`，仅依赖标准库，每次发送新建连接。`mailer.send(to, subject, body)` 可供其他模块调用。

### 消息推送

在「消息推送」添加目标邮箱，选择每 1／2／4 周一次及周日发件时间。统计截止北京时间周六 23:59，每次汇总此前连续的完整周日—周六周期。首次启用安排在下一个可用的周日；修改频率或发件时间会重新安排。保存格式、编辑预览均不会发信，默认关闭定时推送；启用前须在「其他设置 → SMTP」完成发件配置。

- 邮件窗口内双击标题、开头或结尾编辑，可用 `{开始日期}`、`{结束日期}`、`{周期周数}`。示例模式仅用于预览，实际发送始终读取真实考勤。
- 迟到／旷班分别启停；关闭后折叠为一行。各自选择名称、次数、日期时间、本月累计迟到次数、分组。日期时间为班次开始时间，多条记录逐行展示，其余列仅在首行填写；月累计按周期结束日所在月份统计，分组为当前权限组。考勤沿用现有迟到／旷班判定和手动改判。
- 短按列名（松开时不足 350 毫秒）切换升序，再按反向；长按 350 毫秒后拖动调整列顺序，关闭的列固定排在启用列之后。键盘可用 Enter 排序、Alt + 左右方向键调序。
- 后台使用真实北京时间，每 30 秒检查一次，需要保持服务运行；手动系统时间不会触发提前发送。重启保留计划与发送记录；停机错过多次时发送最近一次到期的完整周期。每个周期逐邮箱记录发送状态，成功的不重复发送，失败的 15 分钟后重试。异常中断留下的「发送中／待确认」记录不自动重发，以免重复投递。
- 配置与发送记录存储在 `data` 中的应用数据库内；SQLite 与 MySQL 均自动建表，旧库迁移包含投递记录。`消息推送` 为独立权限选项，可在权限组中授权；原始管理员始终可访问。

## 权限组与访问范围

- **权限组管理**：点击「新建权限组」输入名称，展开组卡片后用树状折叠选择可访问的页面，点击「保存访问范围」对全组生效。支持重命名和删除自建组；删除后该组账号自动转入「会员」。
- **会员**：内置默认组，所有新增账号（含名单补齐、每周排班生成的账号）默认加入。初始开放成员端「概览」下的「打卡、外勤」以及「外勤确认」，「排班列表」需要单独授权；访问范围可编辑，组名固定且不能删除。重复启动不重置已保存的选项。
- **用户管理 → 更改权限**：只选择用户所属的一个权限组，不再逐个用户勾选权限选项。账号列表显示所属组。
- **访问选项**与侧栏对应：成员端依次为「概览、排班列表、外勤确认」，其中「概览」下含「打卡、外勤」两个操作权限；管理端依次为「概览、每周排班、特殊排班、调换值班、外勤管理、用户管理、权限组管理、消息推送、查看日志、数据管理、其他设置」。树采用一行一项的紧凑文件列表，按成员端与管理端缩进折叠，父级支持全选与部分选中。
- **可折叠的子项**：概览下分「查看概览」与「更改考勤状态」；其他设置下分「打卡设置」「SSO 设置」「值班时间」「系统时间」「SMTP」。只勾「更改考勤状态」时概览详情里的人名是只读文本而非按钮，且 `PUT /api/admin/overview/attendance` 只认这一项。
- **「其他设置」没有独立入口**：只要拥有「值班时间」「系统时间」「SMTP」「打卡设置」「SSO 设置」中的任意一项，侧栏就会出现「其他设置」；进入后只显示已授权的那张卡片。五项分别控制 `/api/admin/rules`、`/api/admin/clock`、`/api/admin/smtp`、`/api/admin/checkin-access`、`/api/admin/sso`，服务端各自校验。
- 前端隐藏未授权入口，后端逐接口校验组权限；修改组范围会立即影响全组账号的后续请求。管理端的「用户管理」选项覆盖账号、密码与所属组操作；「权限组管理」单独决定能否维护组定义。
- **原始管理员**继续从 `data/root_admin.json` 验证，固定拥有全部访问范围，不能在组或用户管理中降权，且不占用组成员数。
- 旧账号的独立权限在升级时转换为对应权限组，保留原访问范围；原权限列只用于兼容迁移，用户有效权限以 `member_accounts.group_id` 对应的 `permission_groups` 记录为准。数据库控制台不能直接修改权限列或所属组。


### 打卡设置：来源 IP 限制

管理端「其他设置 → 打卡设置」分别配置打卡和外勤登记的网络规则，使用独立的「打卡设置」权限，原始管理员始终可访问。每行填写一个 IPv4 / IPv6 地址、CIDR 网段、IPv4 子网掩码或 `localhost`（匹配 `127.0.0.0/8` 与 `::1`）。允许模式只放行匹配的地址，空列表禁止全部；排除模式禁止匹配的地址，空列表不限制。默认均为空排除列表。

成员端「概览」始终保留本人当日排班与外勤登记面板，外勤登记位于时间轴下方、排班卡片上方；缺少「打卡」或「外勤」权限时，对应按钮置灰禁用，已有权限配置继续沿用。签到和外勤登记按钮在网络不符合要求时也置灰，后端在每次操作时检查账号权限和来源 IP。成员端每 30 秒以及切回页面时刷新网络状态；账号权限与签到时间窗口仍须同时满足。外勤确认和管理员修改考勤不受这两项登记规则影响。

规则以服务器识别的连接来源 IP 为准，不读取客户端提供的 `X-Forwarded-For` / `X-Real-IP`。现有启动方式禁用代理头解析，反向代理部署时看到的是代理地址；管理页会显示当前识别的 IP。

### 无操作自动退出

管理端「其他设置 → 无操作自动退出」使用「值班时间」权限，分别设置成员端（默认 120 分钟）与管理端（默认 30 分钟）的无操作时限（1～240 分钟），以及两端各自的无响应时限（默认 90 秒，30～3600 秒）。

- 只有真实的鼠标、键盘、滚动或触摸操作会续期；定时刷新、长轮询和心跳都不会延长无操作时限。
- 同一浏览器同一端的多个标签页通过 `localStorage` 共享操作时间，其他设备独立计时。
- 无响应检测由全局心跳承担：登录后每 20 秒向服务器报到一次，超过无响应时限未收到心跳的设备登录会被撤销，页面随即退出。
- 服务端保存的登录租约独立于 Cookie 存在，所以即使 Cookie 仍在有效期内，超时或已注销的凭据也会被拒绝。旧版本升级后已有登录需要重新登录一次。

### GDUTNIC 单点登录

SSO 默认关闭，且身份提供方地址默认为空：本应用不带任何组织专属地址，需由管理员自行填写。管理员在「其他设置 → SSO 设置」（需要独立的「SSO 设置」权限，原始管理员始终可访问）填写身份提供方地址、客户端标识、客户端类型与密钥、精确的登录回调地址，然后打开「在登录页显示 SSO」并保存，两个登录页立即出现「通过GDUTNIC」，无需重启。

- 使用授权码 + PKCE；服务端校验 `iss`、`aud`、`exp`、`nonce` 与 `azp`，签名密钥只从该 issuer 的 JWKS 获取，元数据端点必须与 issuer 同源。
- 账号绑定以 `issuer + sub` 为准，不依赖显示名称。没有匹配记录时跳到绑定页，需要输入本地账号的密码才能完成首次绑定；原始管理员首次绑定也必须验证本地密码。
- 自动匹配默认关闭。管理员可以选择用 `preferred_username`、`name` 或组织自定义字段自动匹配本地用户名，但对已绑定的账号从不复写；被管理员解除绑定的账号不会再被自动匹配，需要重新验证密码。**自动匹配只作用于普通成员账号**：持有任何管理员权限的账号以及原始管理员，都必须先验证本地密码才能绑定，因此仅凭「SSO 设置」权限无法接管管理员账号。
- 管理员可以在「用户管理」中解除绑定（账号列表会标记已绑定的账号）；原始管理员不在用户管理中解除绑定。
- 客户端密钥只保存在服务器数据库里，读取接口只返回「是否已设置」，数据控制台把整组 SSO 配置视为凭据并禁止直接修改。
- 完整配置与 Keycloak 端步骤见 [Keycloak 登录配置](docs/keycloak-setup.md)。

### 实时同步

有人签到（包括连班自动签到）或管理员更改考勤时，服务器发布一个考勤版本号。打开成员概览或管理员概览的页面通过长轮询收到通知后，只刷新发生变化的排班卡片、姓名状态、签到人数、统计数字与时间轴，已打开的考勤详情同步更新，不整页刷新。通知只包含版本号，具体数据仍经各自权限范围内的接口读取。长轮询只在相应页面显示时运行，不参与无操作计时。

- Python 3.10+（建议 3.12）
- MySQL 8.4（默认后端）；SQLite 仅用于迁移兼容与隔离测试

## 配置

运行 `python3 -m server.init_data` 会创建 `data/.env`，按 `.env.example` 生成配置并随机生成两份独立的数据库密码。使用远程数据库时编辑 `data/.env`。环境变量优先于此文件。旧根目录 `.env` 会自动迁移；两处配置不一致时停止并提示合并，不覆盖配置。

| 变量 | 说明 | 默认值 |
| --- | --- | --- |
| `DB_BACKEND` | `mysql` 或 `sqlite` | `mysql` |
| `MYSQL_HOST` | 数据库地址 | `127.0.0.1` |
| `MYSQL_PORT` | 数据库端口 | `3306`（`.env.example` 中为 Docker 的 `3307`） |
| `MYSQL_DATABASE` | 数据库名 | `gdutnic` |
| `MYSQL_USER` / `MYSQL_PASSWORD` | 应用账号 | — |
| `MYSQL_ROOT_PASSWORD` | 仅由 `compose.yaml` 的本地 MySQL 容器读取，应用本身不用 | — |
| `MYSQL_SSL_CA` | 远程 TLS 证书路径（可选） | — |
| `SESSION_SECRET` | 会话签名密钥（可选，缺省写入 `data/session_secret.txt`） | — |
| `SESSION_HTTPS_ONLY` | 设为 `1/true/yes` 时 Cookie 仅经 HTTPS 发送并启用 HSTS | 关闭 |
| `KEYCLOAK_ENABLED` / `KEYCLOAK_ISSUER` / `KEYCLOAK_CLIENT_ID` / `KEYCLOAK_CLIENT_SECRET` / `KEYCLOAK_REDIRECT_URI` / `KEYCLOAK_USERNAME_CLAIM` | GDUTNIC 单点登录的环境变量回退；后台「SSO 设置」保存过配置后以数据库为准。必须显式 `KEYCLOAK_ENABLED=true` 才启用；地址等字段默认留空，需自行填写 | 关闭、字段为空 |

`.env.example` 中列出了上述 SSO 变量的占位值。管理员在「其他设置 → SSO 设置」保存的配置优先于环境变量。

本地 Docker 在空的 `data/mysql/` 中自动创建数据库和账号；远程 MySQL 请事先创建数据库并授予应用账号建表与读写权限；应用启动时会自动建表并补齐新增字段，不会覆盖旧数据。

## 启动

使用本地 Docker MySQL：

```bash
python3 -m server.init_data
docker compose --env-file data/.env up -d --wait mysql
./start.sh
```

Windows 使用 `start.bat`。启动脚本会创建项目内 `.venv`、安装依赖（默认 PyPI 失败时自动尝试国内镜像），初始化 `data/` 并读取 `data/.env`，然后监听 `0.0.0.0:50025`。手动运行 uvicorn 或维护命令也会初始化目录。初始化不会重置现有数据库、密码或配置。

启动脚本会先检查数据库，失败时停止并显示连接地址及处理方法。若出现 `Connection refused`，说明配置的数据库地址/端口未接受连接；本地 Docker 部署请先打开 Docker Desktop（Linux 启动 Docker 服务），执行 `docker compose --env-file data/.env up -d --wait mysql`，再启动应用。可单独运行 `.venv/bin/python -m server.check_database` 检查连接（Windows 使用 `.venv\Scripts\python.exe`）。检查会执行应用原有的建表/升级流程，不重置现有数据；不会自动切换数据库。

手动启动：

```bash
python3 -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m uvicorn server.app:app --host 0.0.0.0 --port 50025 --no-proxy-headers
```

启动后控制台会打印管理员地址（形如 `http://127.0.0.1:50025/a8clrf3j`）。首次打开站点会跳转到该地址创建**原始管理员**；之后的账号在「用户管理」中添加。

### 原始管理员

- **首次初始化时创建一次**，在首次设置页可自定义名称并设置密码；名称留空时使用内置名称「原始管理员」。创建后不会再次生成。
- **权限固定且不可更改**：始终拥有全部权限，不受权限编辑影响；不能停用、删除或改名，也没有任何入口能削弱它。
- **不写入 `member_accounts` 表**：账号只存在于 `data/root_admin.json`，因此「用户管理」与数据管理里都看不到这一行，也没有任何操作按钮。启动时会清掉旧版本可能留下的同名镜像行。
- 旧版 `users` 表只是历史记录，不会迁移成第二个可登录账号，也不会删除任何真实值班账号。
- **凭据单独保存在 `data/root_admin.json`**（权限 `0600`，只存哈希），不写入数据库，因此重置数据库不会丢失；登录时也不经过 `member_accounts`。
- 只有密码可以修改：用原始管理员登录后，在「其他设置 → 原始管理员密码」中操作。
- **已有站点升级时**会在下次启动自动创建原始管理员，并在控制台打印一次性初始密码；用它登录后立即修改即可。
- 改名只需编辑 `data/root_admin.json` 的 `username` 字段（密码哈希保持不变）；该文件就是唯一事实来源。

启动时还会为每周名单及已排班人员补齐缺失账号，也可单独执行：

```bash
.venv/bin/python -m server.provision_members
```

给指定账号补授全部权限（管理员恢复用）：

```bash
.venv/bin/python -m server.grant_admin <账号名>
```

## 数据与备份

- **业务数据**保存在 MySQL；本地 Docker 将 `data/mysql/` 挂载到容器 `/var/lib/mysql`，不再使用命名卷。已有命名卷部署应先导出 SQL 到 `data/backups/`，启动新的空库后导入；不要直接复制运行中的 MySQL 文件。
- 项目 `data/` 保存运行时文件，**不提交到 Git**：
  - `.env`：数据库凭证与本地配置；
  - `mysql/`：本地 MySQL 数据、证书与日志；
  - `mysql-config/runtime.cnf`：按本地文件系统大小写规则生成的 MySQL 配置；
  - `logs/`：运行日志（QQ 机器人等），单个文件超过 10 MB 时自动截断到 5 MB，只保留完整的最后若干行；
  - `session_secret.txt`：会话签名密钥；
  - `weekly_roster.json`：每周名单种子（仅在没有已保存模板时读取）；
  - `imports/`：排班表与 CSV 模板等导入文件；
  - `app.sqlite`、`backups/`：旧版 SQLite 与迁移备份。
  - 会话租约、SSO 绑定与 SSO 配置保存在应用数据库内（不是 `data/` 里的独立文件），因此重置 MySQL 会同时清除这些状态。
- 首次初始化创建 `data/`、配置及 `mysql/`、`mysql-config/`、`imports/`、`backups/`、`logs/`、`certs/` 子目录。SQLite 表和会话密钥按需创建；不生成包含真实人员的种子名单。
- 升级现有部署时，启动过程会补齐新表与字段（`login_sessions`、`keycloak_links`、`keycloak_flows`，以及会员账号的 `sso_id`、`sso_auto_link_blocked`），不会覆盖已有数据；首次加入心跳功能时会清空旧登录租约，所有人在升级后需要重新登录一次。
- SQL 导出统一放在 `data/backups/`，证书放在 `data/certs/`。`MYSQL_SSL_CA` 的相对路径相对于 `data/`。备份 MySQL 使用逻辑备份（如 `mysqldump`），或停库后备份 `data/mysql/`。
- `sql/mysql_schema.sql` 只有建表结构，保留在源码中；`.env.example` 只有占位配置。Git 忽略整个 `data/`，并额外忽略数据库文件、SQL 导出、私钥、证书及人员表格，防止误放到其他目录后被提交。

## 从 SQLite 迁移

先停止旧版应用写入 SQLite，配置好**空的** MySQL 数据库，再执行：

```bash
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m server.migrate_mysql --source data/app.sqlite
.venv/bin/python -m server.provision_members
```

迁移会先备份 SQLite 到 `data/backups/`，再在单个 MySQL 事务中导入并逐表校验，保留密码哈希、班次 ID 与签到时间。目标库非空时停止，任何失败都会回滚。迁移完成后再启动新版服务。

## 安全

- 登录通过 `fetch` 发送 JSON，表单强制 POST；即使脚本未加载，密码也不会出现在网址栏或访问日志中。
- Cookie 信封有效期 4 小时；实际登录由服务端租约控制，默认成员端 120 分钟、管理端 30 分钟无操作即失效，并可随时撤销（改密、停用、解除 SSO 绑定都会立即生效）。
- 管理员登录按来源 IP 与账号分别计数，10 分钟内失败 8 次后暂停 10 分钟；绑定时为管理员账号输入密码同样计入这套限额。成员端密码登录按来源 IP 独立计数：同一来源失败 50 次后暂停 5 分钟，与管理员计数互不影响。
- 登录接口只信任直连地址，不读取可伪造的 `X-Forwarded-For`；打卡网络规则同样只使用服务器识别的连接来源，启动脚本显式禁用代理头解析。
- 已设置禁止页面被嵌套、禁止外链脚本、不发送 Referer、禁止 MIME 嗅探等响应头。
- 公网部署请使用 HTTPS，并设置 `SESSION_HTTPS_ONLY=1`。
- 本项目未内置 WAF 与限流之外的防护，公网部署建议放在反向代理之后。

### 旧版 Wiki 助手（MCP）的边界

连接、OAuth、凭证恢复和聊天需要登录本地成员或管理员账号；目标地址只读取管理员配置，忽略请求和旧会话中的地址。OAuth 元数据中的端点必须与该地址同源，服务端不跟随重定向。管理员仍可配置内网 Wiki，请仅配置可信服务。反向代理部署请保留启动脚本的 `--no-proxy-headers`（同一代理后的用户共享来源限额）。

历史问题的复现与修复记录见 [安全验证记录](docs/security-validation-2026-11-09.md)，性能相关的改动记录见 [内存与运行速度优化](docs/performance.md)。

## 版本与 Git 使用

- 远端：`origin` → `https://github.com/AndyZhang32767/gdutnic-duty-scheduling.git`
- 分支：`master` 为已发布的稳定版本；`dev` 为当前开发分支，新功能先进入 `dev`，验证后再合并到 `master`。仓库里另有一个早期快照分支 `v0.1`，仅作留档。截图、日志、`data/` 等运行时产物都不提交。
- 更新本地代码前先停止正在运行的应用，避免启动脚本升级数据库时与运行中的进程冲突：

```bash
git switch dev
git pull --ff-only
bash start.sh          # Windows 用 start.bat
```

- 检查当前状态与差异：

```bash
git status
git diff                            # 未暂存的改动
git log --oneline --graph -10       # 最近提交
git log origin/master..dev --stat   # dev 相对 master 多了哪些改动
```

- 提交与推送：

```bash
git add -A
git commit -m "简短说明改动内容"
git push                            # dev 已跟踪 origin/dev
```

- 把 `dev` 的改动发布到 `master`：

```bash
git switch master
git pull --ff-only
git merge --no-ff dev
git push origin master
```

- 提交信息沿用现有风格：一行祈使句标题（中文或英文均可），需要时在正文按模块列出关键改动与影响，并注明测试结果。
- `.gitignore` 已排除 `data/`、`.env`、数据库与 SQL 导出、私钥与证书、人员表格、日志以及 `.playwright-cli/`。若 `git status` 里出现这些路径，说明规则失效，应先修正再提交。
- 部署机只需要源代码：拉到新版本后按「一行部署」或「启动」重新执行启动脚本即可，脚本会自动补齐新增表与字段，不会清空已有数据库。
